2.3 Database Foreign Keys & ON DELETE CASCADE Behavior
--------------------------------------------------------------------------------
• Verification:
    - Foreign key 1: child taskId -> tasks(id) ON DELETE CASCADE
    - Foreign key 2: child dependsOnTaskId -> tasks(id) ON DELETE CASCADE
• Behavior:
    - Deleting a prerequisite task deletes the referencing junction row in
      task_dependencies automatically at the SQLite engine level.
    - Dependent task in the tasks table is completely preserved and untouched.
    - Because the junction record is removed, the dependent task automatically
      transitions to unblocked if no other incomplete prerequisites exist.
• Audit Finding: VERIFIED.

    val blockedTaskIds: StateFlow<Set<String>> = combine(
      allTasks,
      allDependencies
    ) { tasks, dependencies ->
      val taskMap = tasks.associateBy { it.id }
      val blockedIds = mutableSetOf<String>()
      for (dep in dependencies) {
        val prereq = taskMap[dep.dependsOnTaskId]
        if (prereq == null || prereq.status != "Completed") {
          blockedIds.add(dep.taskId)
        }
      }
      blockedIds
    }.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptySet())
• Audit Finding: VERIFIED.

  task status transition or dependency addition/deletion. Zero polling or manual
  refresh needed.

6. HIDDEN RISKS & ARCHITECTURAL OBSERVATIONS
--------------------------------------------------------------------------------
1. Dependency Semantics Scope:
   Observation: The engine currently evaluates dependencies under Finish-to-Start (FS)
   logic where prerequisite.status == "Completed". While dependencyType is stored
   ("FINISH_TO_START"), if future phases introduce Start-to-Start (SS) or Finish-to-Finish
   (FF), the evaluator should branch on this field.
   Risk Level: LOW (Current Phase 3 requirement is fully satisfied).

2. Cycle Detection Query Scope:
   Observation: In WorkspaceRepository.addDependency, all dependencies across all projects
   are fetched via getAllDependenciesOnce() for the BFS queue. Because same-project
   constraints are already enforced beforehand, this is mathematically sound, but
   filtering by projectId at the query level is recommended if the database grows to
   tens of thousands of dependencies.
   Risk Level: LOW.
